# Architecture decisions

- ADR-001: Modular Rust monolith with domain and exchange boundary crates. Additional modules follow validated workflows; avoid premature services.
- ADR-002: Rust 1.90.0, edition 2024; Node 22+ and pinned TypeScript dependencies. Commit lockfiles and use locked installs in CI.
- ADR-003: Simulation and paper are the only representable modes. No live adapter or write API in M1.
- ADR-004: Integer ticks/lots for executable values; venue scale/filter validation follows in M2. Fees stay in actual asset units.
- ADR-005: PostgreSQL for durable state; Parquet for future event datasets. Session-scoped idempotency keys and replay sequence are explicit. Ledger schema does not yet implement accounting.
- ADR-006: Node built-in HTTP server minimizes foundation dependencies. Read-only loopback API; dashboard deferred.
- ADR-007: Verified Binance official REST documentation on 2026-10-17: LIMIT_MAKER is post-only and rejected if it immediately takes liquidity. No exchange implementation is included. Revalidate current symbol filters, authentication, timeout/unknown outcomes and stream sequencing before implementing the relevant adapters.
  Source: https://github.com/binance/binance-spot-api-docs/blob/master/rest-api.md (New order / LIMIT_MAKER). This review does not establish an implemented or tested Binance integration.
- ADR-008: Starting capital is a research assumption. No live pilot until realistic net-cost validation and separate approval.

- ADR-009 (M2): A dedicated Rust public-data process owns Binance transport, order-book state, recording and replay. TypeScript reads a versioned, atomically replaced status file, avoiding exchange logic and per-request Rust subprocesses in the API. Health remains process health; market readiness is separate. A missing/bad file returns 503, and stale data clears quotes even if the collector stops.
- ADR-010 (M2): Reviewed official [WebSocket documentation](https://github.com/binance/binance-spot-api-docs/blob/master/web-socket-streams.md#how-to-manage-a-local-order-book-correctly) and [market-data-only endpoints](https://github.com/binance/binance-spot-api-docs/blob/master/faqs/market_data_only.md) on 2026-10-17. Open the stream first, buffer deltas, retrieve up to 5000 levels/side, retry snapshots older than the first buffered U, discard u <= snapshot ID, then require U <= local_id + 1 <= u. Absolute quantities replace levels; zero deletes. A gap invalidates the whole book and forces a new connection and snapshot. Ping payloads are echoed in pong frames. Connections rotate after 23 hours, before the documented 24-hour limit.
- ADR-011 (M2): Public normalized prices/quantities use exact 1e-8 units. These are data units, not executable instrument ticks/lots. BTCUSDT/ETHUSDT are the only enabled symbols. Reject unsupported precision; venue filter metadata/conversion must precede future executable orders. `DepthProtocol` separates venue decoding from normalized book/record/replay logic; existing M1 exchange traits remain unchanged. Other venues must provide their own adapter and map their sequencing semantics explicitly.
- ADR-012 (M2): Raw UTF-8 messages and normalized events share a versioned record envelope with process recording ID, connection-session UUID, record sequence and receive/exchange milliseconds. Received and applied events are distinct: buffered arrivals can precede snapshots without changing replay order. Snappy Parquet segments begin with pre-event checkpoints and carry SHA-256 sidecars. Replay verifies checksums and record continuity within each segment. No claim of total exchange history across evicted segments or independent sessions.
- ADR-013 (M2): Bound the transport queue, snapshot buffer, message size, levels and retained segments. An overflow/gap invalidates and reconnects; recording failure halts the affected symbol and removes its quotes. No silent level trimming. Complete order-book coverage is never claimed outside the initial 5000-level snapshot boundaries.
- ADR-014 (M2): Public retry defaults: 3–60 second connection backoff, at least 15 seconds between snapshot requests per symbol, and REST 418/429 Retry-After cooldown (1 second to 7 days; default 60 seconds if absent). These conservative per-process limits do not coordinate with other applications on the same public IP. TLS and artifact verification remain enabled; HTTP CONNECT proxies are supported for WSS, without proxy credential extraction.
